# Engine and host protocol

The MoonBit root package owns filename parsing, ordering, immutable history checks, schema drift detection, planning and execution order. JavaScript owns file bytes/SHA-256, SQLite connections, bindings, snapshots, authorizer callbacks and asynchronous backup.

`Driver.call(operation, arguments)` returns a JSON value or raises `MigrationError`. `prepare(driver, request)` loads immutable SQL, opens `source`, acquires the write lock for `apply` (a read transaction for other commands), and checks history. `Prepared` retains both the schema fingerprint and the complete history snapshot. Advisory rehearsal closes its source read transaction before backup so it does not hold readers across asynchronous work. If `Prepared.backup_required` is true, the host makes a consistent backup through a separate read-only connection and opens a clone of the completed backup. `complete(driver, prepared)` verifies the clone's fingerprint and history before executing anything, then performs rehearsal and real execution. Always release connections and roll back any surviving transaction in a `finally` block, including when preparation fails. Callers using the lower-level `status`/`inspect` helpers directly should own a read transaction around the entire operation.

The Node bridge exposes `prepare_json`, `complete_json` and `plan_json`; these are transport functions. Applications should use the queued `run` entry point, which owns connection lifecycle and reports.

`runInWorker(request, options)` owns a fresh Worker per call. It captures primitive request values and absolute paths before structured cloning, invokes the same `run` lifecycle inside the Worker, and resolves after the thread exits. JavaScript contexts have isolated FFI callbacks and queues; SQLite write locks coordinate contexts targeting the same file. Node's default worker argument inheritance is preserved. Only eval/stdin callers' `--input-type` is removed when a file Worker needs explicit arguments.

Both entry points accept a synchronous `onProgress` observer. Events describe session, preparation, backup page counts, scripts, checks, validation and commit operations. Immutable events have sequence numbers and UTC timestamps; they omit SQL and row values. Observer failures become at most 16 unique diagnostics rather than transaction failures. In-process warnings are saved with the backup report. Worker parent observer warnings are attached to the returned report, after the worker has written its report file.

The worker publishes its final report after runtime cleanup, and the parent waits for exit before resolving. A final report wins over later exit errors because it already records the outcome. If an apply worker starts but exits without a final report, the parent conservatively returns `commit_outcome_unknown`, with the last completed backup path if observed. Progress notifications alone do not authorize retry. No forced termination or worker pool is exposed.

## Cooperative cancellation (0.4.0)

Both entry points capture `options.signal`, a Node AbortSignal. The shared internal session owns queueing, cleanup and report persistence. Direct calls poll the captured signal; workers poll an atomic Int32 flag in a SharedArrayBuffer. The parent registers one abort listener and removes it on worker exit or creation failure. Signals, callbacks and abort reasons are never structured-cloned or put into reports.

Cancellation is checked before queue execution, before host operations, after start notifications, in SQL authorizers and after asynchronous backup. It raises the typed MoonBit `Cancelled` error, serialized as `kind: cancelled` with exit category 4. Cleanup bypasses cancellation polling so active transactions are rolled back and connections close. A backup that completed before cancellation remains a complete backup; the cancellation report is persisted beside it.

An active SQLite VM operation, busy wait or backup can finish before a cancellation checkpoint is reached. This release does not interrupt native calls or terminate workers. Cancellation before source COMMIT rolls back; cancellation arriving after a completed COMMIT preserves success. `commit_outcome_unknown` takes precedence over an abort request when acknowledgement is lost. The parent never infers rollback from an abort flag if a worker exits without a final report. In-process synchronous SQLite work delays timer/signal callbacks, so use workers for responsive UI or timeout cancellation.

| `inspect` | `id` | `SchemaSnapshot` with raw schema objects and SQLite metadata |
| `fingerprint` | `id` | SHA-256 of deterministically ordered schema objects |
| `sequences` | `id` | Business tables as `{name, seq?}`; omit absent seq, use decimal Int64 strings |
| `exec_script` | `id, sql, filename` | null; guarded SQLite statement parsing/execution, no unbound parameters |
| `exec_check` | `id, sql, name, filename` | null; one read-only query returning exactly one INTEGER 1 |

| `validate` | `id` | null only when foreign_key_check is empty and quick_check is `ok` |
| `verify` | `id` | `{integrity_check: "ok", foreign_key_check: "ok"}` after full read-only validation |
| `clock / timestamp` | empty object | Decimal string of monotonic milliseconds / UTC ISO-8601 string |

Fingerprinting excludes SQLite-owned objects and the migration history table; it detects schema edits, not business-data changes. Column/index/foreign-key metadata is retained separately by inspection. Node query results preserve large integers as `{$int64: "decimal"}` and bytes as `{$blob: "base64"}` when transported as JSON; SQLite performs migration data copies directly without converting through JavaScript numbers.

History columns are `version` (integer primary key), `name`, `checksum`, `applied_at`, `duration_ms`, `schema_before`, `schema_after`, and `tool_version`. Its name is `__moonmigrate_history`. The Node adapter requires its exact engine-owned DDL and rejects attached triggers or extra indexes, including case-insensitive name collisions. The engine verifies adjacent schema fingerprints form a chain and durations are nonnegative. Checksums and fingerprints detect accidental drift; they are not signatures against a malicious actor with database write access.

Before and after each migration the engine compares AUTOINCREMENT sequence floors for tables retaining the same name. A lower or missing sequence fails the whole transaction; values never pass through JavaScript floating-point numbers. Intentional table deletion is permitted. Renames require reviewed SQL to move the appropriate sequence floor, since the executor cannot infer table identity from arbitrary SQL. Scripts should restore floors before inserting additional rows.

The MoonBit JSON codec represents `Int64` as a decimal string. Clock values and the `duration_ms` report field therefore use strings at the transport boundary; the adapter binds durations as SQLite integer values through JavaScript BigInt.

Reports include `ok`, a command/result or failure `kind`/`message`/`exit_code`, execution stage, and persistent backup/report paths when available. Exit categories are 0 success, 1 input/database/runtime, 2 history/policy, 3 lock timeout and 4 cancelled. On uncertain COMMIT outcome, inspect the history through a fresh invocation before deciding whether another forward migration is needed.

`run(request)` captures primitive values and resolves paths at invocation time, before entering the context-local queue. Host-only options are `busy_timeout_ms` (integer 0–2147483647, default 5000) and `backup_dir` (apply only, default `<db>.moonmolt-backups`). They configure the Node adapter and are not fields in the MoonBit `Request`. Both CLI and library reject inappropriate creation/inspection options. The shipped `runtime.d.mts` describes library requests and result unions. SQLite operations are synchronous in their executing context; use `runInWorker` when the caller's event loop must remain responsive.

Planning accepts the pinned upstream JSON format. Table arrays `columns`, `indexes`, `foreign_keys`, `checks`, `triggers`, and root `views` must be present; absent optional defaults/actions or JSON null are supported. Rename hints use `{"tables":[["old","new"]],"columns":[["target_table","old","new"]]}`. SQL expressions for defaults are trusted author input, not untrusted user input.

The native implementation is reserved behind `Driver`; this release ships the Node adapter only. MoonMolt does not claim arbitrary SQLite DDL can be losslessly transformed into the upstream model.

## Application embedding and preconditions (0.5.0)

The Node request may supply `migrations: readonly MigrationFile[]` instead of `dir`. Each entry has `filename`, `sql` and optional `checks_json` strings. The host snapshots and validates them synchronously before queueing or worker creation, rejecting caller-supplied checksums and unknown entry fields. Both file and bundle loaders use one UTF-8/checksum implementation. SQL and checks text retain BOM and line endings; lone Unicode surrogates cannot silently become UTF-8 replacement characters. `checks_json` is raw sidecar text to preserve existing byte hashes when changing loaders. The complete immutable prefix must be supplied, including already-applied entries; an empty bundle does not bypass existing history validation. No filesystem migration directory is consulted in bundle mode. This remains a host-only source option; MoonBit receives the same `MigrationSource[]` via `load`.

MoonBit `Request` adds optional `expected_application_id: Int?` and `expected_version: Int?`. Record constructors must supply `None` when unused; JSON may omit them. Custom drivers must now implement `application_id` and include `application_id: Int` in `SchemaSnapshot`. `Prepared` also retains that value; the engine compares the backup clone's application ID, history and schema with preparation. A changed ID between advisory preparation and backup fails with `HistoryMismatch`, even when its schema and history are unchanged.

The engine checks expected identity after opening its write/read transaction and expected version after reading canonical history, before backup, rehearsal, history initialization or any migration. Both are also enforced on no-op calls. Version 0 means empty MoonMolt history and gaps are permitted (not SQLite `user_version`). Failed conditions raise `Policy` with expected and observed values. Identity accepts the full signed 32-bit range; expected version accepts 0–999999 and is rejected for inspection. The host validates numeric input before JSON decoding. Neither guard assigns metadata; an application owns initialization of its own new database's ID. New databases have ID 0, including `apply --create`; a nonzero identity expectation deliberately rejects them until the application has initialized them. An explicitly created file may remain empty after a rejected operation.

`status` and migration no-op reports include `application_id` and `current_version` observed during preparation. Normal completed batch report shapes are unchanged. An identity is a file-format hint, not a tenant identifier or cryptographic proof. The version condition intentionally prevents a second caller from silently succeeding with a stale deployment assumption; ordinary idempotent startup can omit it. On unknown COMMIT outcome, obtain fresh status without the stale expected version before making a retry decision. Scripts still cannot assign PRAGMAs to bypass identity checks.

## Reviewed schemas and TEMP namespaces (0.8.0)

`Request` adds `expected_fingerprint: String?`; MoonBit record constructors must supply `None` when unused, while JSON may omit it. Both host capture and core preparation reject anything other than exactly 64 lowercase hexadecimal characters before host work. After obtaining its owning transaction, the core reads the current fingerprint once, checks history drift, then compares this optional expectation before backup, full verification or migration execution. Inspection compares its snapshot's fingerprint. All database commands and no-op calls enforce the condition. Normal history drift remains `HistoryMismatch`; a failed expectation raises `Policy`. No new driver operation is required. The low-level `status` helper and prepared status/verify/no-op reports now include `fingerprint`.

The expectation is useful before a legacy database has any migration history. It describes the initial schema, not a desired final schema or row-data hash. A schema-changing upgrade makes the old expectation stale even for a subsequent no-op. A caller must deliberately use an already trusted new schema or omit the condition for ordinary idempotent startup; automatically reading a rejected file and retrying with its hash defeats the review. App ID, version and fingerprint conditions are independent. Fingerprints are not signatures or tenant identifiers, and equivalent DDL text is not canonicalized.

The Node host now hashes the same ordered `{type,name,tbl_name,sql}` objects directly from `main.sqlite_schema`, retaining the previous hash algorithm and exclusions without enumerating columns/indexes on each fingerprint request. Detailed inspection explicitly qualifies its metadata PRAGMAs with `main` so TEMP objects cannot redirect them. Existing history fingerprints and checksums remain compatible.

SQLite searches TEMP before main for unqualified names ([naming rules](https://www.sqlite.org/lang_naming.html)). A reproduced migration copied `main.orders` to a same-name TEMP table, cleared main amounts and passed a check against the unchanged temporary copy. After each statement that creates/renames tables or creates views/virtual tables, the host checks current main/TEMP table and view names with SQLite `COLLATE NOCASE` and rejects collisions. The callback runs before later SQL can remove the conflicting helper. This policy deliberately also rejects intentional table/view shadowing with qualified queries; use distinct helper names instead. Distinct temporary tables can span scripts, and same-name indexes in separate schemas and SQLite-owned internal objects remain supported. The authorizer stays active throughout compilation and execution; clone and source failures roll back their respective owning transactions.

## Current business verification (0.9.0)

`Request` adds `verify_checks: Array[MigrationCheck]?`, accepted only with command `verify`. MoonBit constructors supply `None` when unused; JSON can omit it. Provided lists must be nonempty with unique nonempty names and SQL. The Node capture layer snapshots primitive names/SQL before queueing or worker creation, rejects unknown rule fields, NUL SQL and invalid Unicode, and shares manifest validation with migration sidecars. CLI `--checks-file` loads a strict UTF-8 JSON object containing only a nonempty `checks` array; it does not load a preservation group or infer a historical sidecar.

After identity, version, history and fingerprint checks and full SQLite validation, the MoonBit core calls existing `exec_check` operations for each supplied rule, with `id: source` and `filename: verify`. This stays in the original read transaction, so an intervening WAL commit cannot make a custom rule see newer rows than the verified schema/history snapshot. Custom drivers supporting this option must implement the existing read-only scalar `exec_check` contract; no new operation is introduced. Success reports always include `checks: [{name, ok: true}]`, empty when omitted. Failures use Policy/exit 2, never a partial verified success. Progress remains in stage prepare and exposes rule names rather than SQL/results. Cancellation uses the existing cleanup path.

These are explicit current application assertions, not immutable migration definitions. They do not enter checksums or history and do not cause pending SQL, historical checks or preservation captures to run. Choose rules appropriate to the selected snapshot's schema and expected business state. A successful query only establishes its authored predicate; nondeterministic SQL and insufficient predicates remain the caller's responsibility. Verification owns a read-only connection and creates no backup.

The statement-boundary namespace guard also rejects resulting main/TEMP objects under `__moonmigrate_`, except the canonical main history table. This closes a rename gap: SQLite's [`SQLITE_ALTER_TABLE` authorizer arguments](https://www.sqlite.org/c3ref/c_alter_table.html) identify the database and old table, so authorizer name checks alone cannot reject the new protected name. The schema check runs immediately after affected DDL, before later SQL can conceal it. The reserved namespace remains unavailable for application objects.

## Business verification (0.2.0)

`MigrationSource` and `Migration` now have `checks: Array[MigrationCheck]?`; `MigrationCheck` contains `name` and `sql`. Existing host JSON may omit `checks`. MoonBit callers constructing these records must provide `checks: None` for SQL-only migrations. A custom driver must implement `exec_check` if it supplies checks; the engine invokes it after each script and sequence validation, before recording history. A failure must raise `Policy` and leave the owning transaction to be rolled back. Successful batch reports include `checks` entries with migration version, filename, check name and `ok: true`. No-op batches do not rerun checks.

The Node host reads `<migration basename>.checks.json` together with SQL. Its format is a nonempty `checks` array of uniquely named `{name, sql}` objects. Orphan files, unknown fields, symlinks and malformed JSON/UTF-8 are rejected. Without a sidecar the checksum stays `sha256(SQL raw bytes)`. With one, the checksum is SHA-256 over the UTF-8 string `moonmolt-checks-v1\0<SQL SHA-256 hex>\0<checks SHA-256 hex>`; the separators are literal NUL bytes. Whitespace changes in a checks file therefore invalidate applied history as SQL edits do.

The SQLite authorizer allows only read/select/function/recursive-query operations on the current database and its temporary tables, excluding reserved metadata access. The prepared statement's `sourceSQL` identifies the first SQLite-compiled statement; any tail containing more than comments, whitespace or empty terminators is rejected. The host fetches at most two rows as arrays with BigInt INTEGER values, so duplicate column labels and enormous result sets cannot conceal a malformed boolean result. SQL errors and unexpected results become policy failures naming the migration and check. Business rules are authored queries, not proofs of arbitrary data preservation; write accurate conditions rather than unconditional `SELECT 1` checks.

## Preservation and query hardening (0.6.0)

`MigrationSource` and `Migration` add `preserve: Array[MigrationCheck]?`; MoonBit record constructors must supply `None` when unused. The sidecar accepts nonempty `checks` and/or `preserve` arrays, with unique names across both. Existing manifests and the checksum domain remain unchanged. SQL and optional sidecar bytes are captured once by either loader. Neither adding a preservation group to applied history nor changing it later is permitted without a new migration.

Before each script, the core captures its preservation queries inside the same transaction, then runs SQL, sequence protection and ordinary checks. It captures the same queries again and compares the typed JSON values exactly before recording history. Each successful rule appears in `BatchResult.preserved` with version, filename, name and `ok: true`. The core performs this independently for clone and source; source baselines are not copied from the clone. A mismatch raises `Policy` without putting either value into the error. A subsequent migration is free to change values unless it declares its own preservation rule. No-op calls do not recapture data.

Custom drivers implementing preservation must provide `capture_value` with a deterministic typed encoding. The Node encoding is `{type: 'integer', value: '<Int64 decimal>'}`, `{type: 'real', value: '<finite roundtrip decimal>'}`, `{type: 'text', value: '<decoded string>'}`, `{type: 'blob', value: '<base64>'}`, or `{type: 'null'}`. Integer and REAL 1 are distinct. Real zero signs compare equally. Text and blob values are limited to 1 MiB before transport; this limits retained scalar size, not SQL computation or SQLite's internal allocations. For byte-exact text comparison authors can query a BLOB cast; decoded text is not a proof about invalid UTF-8 bytes. Queries must return exactly one row and one column, with at most two rows consumed. Nonfinite reals, writes, additional statements, reserved metadata and malformed cardinalities fail closed. Results are transient and omitted from reports, saved backup reports and progress events; the latter expose only name and before/after phase.

Boolean checks and preservation share a read-only scalar executor. It also rejects all unbound placeholders. A reproduced regression used `NOT EXISTS(... WHERE amount < :minimum)` after clearing amounts: SQLite silently treated the missing parameter as NULL and returned INTEGER 1. The host now compares the fresh statement's `expandedSQL` with `sourceSQL` before execution; actual parameters expand to NULL while placeholder-looking text in literals, quoted identifiers or comments remains unchanged. No application values are bound or interpolated. This uses SQLite's parser rather than a SQL-text regular expression. See [Node expandedSQL](https://nodejs.org/api/sqlite.html#statementexpandedsql) and [SQLite expanded SQL](https://www.sqlite.org/c3ref/expanded_sql.html).

An aggregate comparison is only as strong as the authored query. Counts/totals do not guarantee all rows are unchanged; ordered identity or field sets may be needed. Avoid nondeterministic or connection-dependent expressions and use explicit ordering for aggregate collections. Cancellation checkpoints, transaction ownership and uncertain COMMIT reporting remain the same.

## Scripts and read-only verification (0.7.0)

The script review reproduced the same unbound-parameter problem in the migration body, independently of checks. A two-migration regression created and updated a new table, then assigned an unbound placeholder to an existing account balance. Version 0.6.0 accepted it and SQLite wrote NULL. The host now lets SQLite compile one statement against the current transaction schema, uses `sourceSQL` for the exact compiled prefix and rejects a changed `expandedSQL` before executing that statement. It then executes the compiled prefix with `exec`, so SELECT and RETURNING are fully consumed. Later statements can depend on earlier DDL. The authorizer remains active during compilation and execution, and each boundary polls cancellation and checks transaction ownership. Triggers are parsed as complete statements by SQLite; no semicolon splitter or substitute SQL grammar is used. A small leading-trivia scanner handles empty terminators, whitespace/BOM and comments, including SQLite's accepted unterminated trailing block comment. All SQL bytes used for history checksums remain unchanged. This adds a compile step per statement; it is not a bulk data-import interface.

`Request.command = "verify"` reuses the normal source loader and preparation checks, opens the source read-only, owns a read transaction and enforces identity/version conditions, canonical history and schema drift. The core calls the host `verify` operation and checks its summary before reporting success. `Prepared.backup_required` is always false, including when migrations are pending, so completion never opens a clone or runs migration/check/preservation SQL. Mutation and target options (`create`, `rebuild`, `to`, host `backup_dir`) are rejected. The existing `status` command remains a metadata check rather than a full integrity check.

The Node driver runs `foreign_key_check` and full `integrity_check` for verify. Migration commit validation retains `quick_check`. Both paths stream at most 21 finding rows, show up to 20 and explicitly mark omitted diagnostics; full/quick integrity PRAGMAs also use an error limit of 21. A success summary requires no foreign-key findings and exactly one integrity result `ok`. The bound limits findings stored and reported, not the cost of scanning a healthy database. Full checking can detect index/table inconsistencies that quick checking omits, as demonstrated with a deliberately inconsistent index fixture.

The read transaction keeps history, schema and validation on one WAL snapshot while another process may commit a newer state. Progress adds `operation: verify` in stage `prepare`. Workers, observers, lock timeout and cooperative cancellation use the same lifecycle; an active SQLite VM scan is not forcibly interrupted. Success reports include `command: verify`, `verified: true`, `database_modified: false`, `application_id`, `current_version`, `applied`, `pending` and `validation`. Pending entries are informational, not an indication of invalidity. No backup or report file is created. The command does not rerun historical business checks or certify pending SQL, business correctness, backup provenance or tenant identity. Custom drivers must implement `verify` to support this command; the MoonBit public record shapes are unchanged in this release.
