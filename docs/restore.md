# Restoring an upgrade backup

1. Stop the application and every process using the database. Confirm no connection remains open.
2. Read the adjacent JSON report and choose the backup made immediately before the intended upgrade. The backup is a complete SQLite snapshot, including committed WAL contents and the migration history at that time.
3. Verify the selected snapshot using `moonmolt verify --db backups/before.sqlite --dir migrations --worker --format json`. Use the original unchanged migration prefix, optionally adding the application's known `--expected-application-id` and expected historical version. Pending migrations are normal for a pre-upgrade backup; verification never applies them. A successful check confirms history/schema, full SQLite integrity and foreign keys for that snapshot. Also confirm the backup belongs to the intended user/database; application IDs identify file formats, not individual tenants.
4. Preserve the current database and any `-wal`, `-shm` or `-journal` sidecars in a separate location while all connections are closed. This retains the post-upgrade state for investigation.
5. Replace the original database file with a copy of the chosen backup. Do not leave sidecars from the replaced database beside the restored file. Restore appropriate filesystem permissions.
6. Run `moonmolt verify --db app.db --dir migrations --worker` against the restored file and inspect the application's important records before restarting. This opens a read-only connection and does not replay the historical business checks, since those conditions described earlier migration-time data. A failed verification is not a repair instruction; keep the evidence and investigate before using the restored file.

Restoration replaces the whole database, including any data written since the backup. It is an operator action, not an automatic down migration. MoonMolt's automatic backups are retained until the operator removes them; plan storage retention for the application.

For current application assertions, add `--checks-file application-health.json` to verify. The file has `{"checks":[{"name":"positive amounts","sql":"SELECT NOT EXISTS(SELECT 1 FROM main.orders WHERE amount_cents<=0);"}]}`. Adapt it to the selected backup's actual schema and expected state; a pre-upgrade snapshot may not have new columns. These explicit rules run after SQLite validation in the same read snapshot and report Policy/exit 2 on failure. They do not replay historical migration rules, repair data, or change the snapshot. The example predicate permits an empty table; add a count rule when existence matters.

A running SQLite database must not be backed up or restored using ordinary file copies. MoonMolt creates its snapshot through SQLite's backup API; only the completed standalone backup is copied into the rehearsal database.

Since 0.9.1, newly created backup directories use POSIX mode 0700, and snapshots and report files use 0600, subject to umask. Existing directory permissions are managed by the application/operator. Windows uses inherited directory ACLs; select a suitably private backup directory there. The snapshot path is exclusively reserved before SQLite opens it and before its start progress event. A filename collision aborts before migration SQL, preserves the existing file and does not claim it as a backup or incomplete backup. This reservation does not defend against another process that already has write access to the backup directory and changes files afterward.

Since 0.9.2, verify also compiles persistent view queries and trigger write paths without executing their writes. A snapshot with an unresolved view/trigger or a compiled program accessing protected migration metadata fails Policy even when SQLite's integrity check alone would report ok. Keep the failed snapshot for investigation and review an explicit forward repair; verification does not remove or rewrite definitions. It still does not prove arbitrary trigger business semantics.

A completed snapshot made before a repair intentionally retains the original broken definition. It can fail definition verification while still being a complete, consistent backup; this is different from an incomplete_backup caused by interrupted backup creation. Select a known-good snapshot or investigate an explicit repair rather than treating backup completion as proof that the old schema was usable.

Only a returned `backup` denotes a completed snapshot. A reserved empty or partially written file may be retained as `incomplete_backup` after backup I/O failure; never restore it. A missing JSON report or `report_warning` is separate from transaction outcome: a successfully committed migration remains successful if its report cannot be saved, and the completed SQLite backup remains available. Report files are also created exclusively; an existing report is preserved. Confirm the returned outcome/history before any retry.
